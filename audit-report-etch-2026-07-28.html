📝 总体评估

📋 总体评估

项目概况：Etch 是 Apple Silicon macOS 上的 Electron 43 + React 19 + TypeScript 5 本地英中双语硬字幕工作站。代码已经形成可运行纵切：任务清单以 task.json 为权威源，SQLite 是可重建投影，媒体工具与四类本地 Agent CLI 经进程组和 durable run registry 管理。

主要风险：最危险的不是缺少某个边缘功能，而是权限边界与恢复承诺不一致：可配置 renderer URL 没有 IPC sender 校验，Full Disk Access 进程宿主以 Electron 的 Node 模式运行；同时阶段先覆盖 canonical 产物再做 lease/CAS 提交，正常退出又会把仍有 detached worker 的实例标记为 clean。

亮点：窗口启用了 sandbox、contextIsolation 并关闭 nodeIntegration；preload API 较窄，Zod 边界校验、原子写入、文件 realpath/inode/hash 校验、Provider text-only 隔离、进程身份核验和大量不变量测试均明显高于普通 MVP。

优先修复：先封闭 renderer/IPC 与 Full Disk Access 进程边界，再把所有阶段改成候选产物提交协议、实现退出 drain/stop、隔离坏 manifest 与重复 task ID、限制进程输出内存。之后再补齐公开发行链、长视频切片、配置契约和 CI。

总评：C（4.5/10）——这是一个工程底座认真、测试资产可观的个人 MVP，但当前不满足“稳定公开发行”的门槛。评分并非否定纵切可用性，而是反映 High 风险集中在权限、原子性、恢复和分发这些不可由 UI 绿灯掩盖的边界。

审计基线与漂移：发现以提交 fed6f5b921b271b50e8bb36fdda4282e4956611a 为基线。审计期间工作树出现并行未提交改动：src/core/translation.ts、src/main/pipeline/task-pipeline.ts、tests/pipeline-glossary.test.ts、tests/translation.test.ts（当时统计 +193/-6），并在报告收尾前形成 commit 276635ebd704aeaa76f322f185194ba2992b6c22；本报告未覆盖或修改这些漂移，涉及行号以原始基线为准。

F-01. Full Disk Access 与 Electron RunAsNode 进程宿主形成过宽权限继承

HighConfirmed
🎯 Confidence: High📁 Security / Privacy📍 src/main/runtime/process-runner.ts:225-244🧭 外部进程宿主

问题：packaged app 中 process.execPath 是 Etch 主二进制；代码为它注入 ELECTRON_RUN_AS_NODE=1 并用 -e 执行 JavaScript，同时 App 引导用户授予 Full Disk Access，打包配置却没有关闭 RunAsNode fuse。

为什么重要：任何能启动该本地二进制的同用户进程都可把它复用成带 Etch TCC 身份的通用 Node 解释器；这是一条直接的权限借用路径，不需要先控制 Etch renderer 或 tool override。

现实失败场景：Etch 已获 Full Disk Access；另一个普通本地应用或脚本用 ELECTRON_RUN_AS_NODE=1 和 -e 启动 Etch 主二进制，借 Etch 身份读取 Chrome 数据库或其他 TCC 保护文件。

process-runner.ts:225-244 const command = hostIdentity ? process.execPath : spec.command const env = hostIdentity ? { ...(spec.env ?? process.env), ELECTRON_RUN_AS_NODE: '1' } : spec.env spawn(command, args, { env, detached: true, ... }) App.tsx 同时提供并首启展示“完全磁盘访问”入口；对已安装 Etch.app 的无害探针实际输出 RUN_AS_NODE=v24.18.0。
最小修复
在打包阶段关闭 RunAsNode（并评估 NodeCliInspect）fuse；停止把 Etch.app 主二进制当 Node host，改用独立、最小权限、固定身份的 helper 或受控 utility process。
更好的长期修复
把 Chrome cookie 访问、媒体工具和 Agent provider 拆成不同权限 helper，使用明确 IPC 协议和最小环境；主 UI 进程不承担通用执行宿主角色。
⏱ 预计工作量： 2–5 天  ·  回归测试：打包态测试 helper 身份、FDA 继承矩阵、恶意 override 拒绝，以及主 bundle 二进制不以 RunAsNode 执行。

F-02. 生产窗口信任任意 renderer URL，IPC handler 未校验 sender

HighConfirmed
🎯 Confidence: High📁 Security📍 src/main/index.ts:62-87, 141-417🧭 BrowserWindow / IPC

问题：只要环境中存在 ELECTRON_RENDERER_URL，包括 packaged app，主窗口就加载该 URL。所有 ipcMain.handle 直接处理调用，没有检查 event.senderFrame.url 或 webContents.id。

为什么重要：安全的 sandbox/contextIsolation 无法弥补“任意远程页面获得 preload 能力”这一信任错误。

现实失败场景：用户从带该环境变量的终端启动 Etch，或启动环境被本地软件污染；远程页面通过 preload 调用设置、工具检测、任务创建/删除和 Full Disk Access 跳转等高权限 IPC。

最小修复
仅在 !app.isPackaged 的开发模式读取 ELECTRON_RENDERER_URL；封装 registerTrustedHandler，逐次断言 sender === mainWindow.webContents 且 URL 为打包 file:// 页面或固定开发 origin。
更好的长期修复
建立 capability 分组的 IPC 注册层，统一 sender、schema、审计日志与敏感动作确认；对导航、新窗口和外链添加 deny-by-default policy。
⏱ 预计工作量： 4–8 小时  ·  回归测试：packaged 模式忽略远程 URL；伪造 webContents 和非受信 origin 调用每类 IPC 均被拒绝。

F-03. 阶段在 lease/CAS 提交前覆盖 canonical 产物

HighConfirmed
🎯 Confidence: High📁 Data Integrity / Concurrency📍 src/main/pipeline/task-pipeline.ts:240-319, 338-498, 1127-1198🧭 stage commit protocol

问题：#perform 先写/rename 到 source.mp4、probe.json、zh_cues.tsv、final.mp4 等 canonical 路径，之后 commitLease 才核对 revision、fingerprint 与 lease。

为什么重要：CAS 只保护 manifest，不保护已经覆盖的文件；提交失败后，manifest 仍指向旧 hash，磁盘文件却已变化。

现实失败场景：阶段运行期间用户校对或另一 mutation 增加 revision；FFmpeg 完成并覆盖 final.mp4，随后 lease 提交报 stale。旧“有效”artifact 元数据从此与文件不一致，后续读取/恢复阻断。

最小修复
每个 stage 写入 runId/versioned candidate 路径；commitLease 成功的同一序列化临界区内发布 artifact 引用。失败时删除 candidate，永不覆盖当前 manifest 指向的文件。
更好的长期修复
统一 ArtifactTransaction：prepare → hash/fsync → CAS manifest publish → 延迟 GC；canonical 名称只作为由 manifest 解析的逻辑名。
⏱ 预计工作量： 2–4 天  ·  回归测试：在每个写文件阶段注入并发 revision mutation，断言旧 artifact 仍可按 hash 读取、candidate 被清理、manifest 不指向被覆盖内容。

F-04. 正常退出标记 clean，却未停止 detached 外部 worker

HighConfirmed
🎯 Confidence: High📁 Stability / Cost📍 src/main/index.ts:127-134; src/main/runtime/process-runner.ts:225-245🧭 app lifecycle

问题：所有外部命令均以独立 process group 启动；before-quit 只关闭 SQLite 并写 cleanExit=true，没有 drain、取消 pipeline 或等待 run registry 清空。

退出前若 registry 非空，显示“完成当前原子步骤 / 立即停止 / 取消退出”；选停止时按已验证身份终止所有当前实例进程组并等待 registry 持久化清空，再 markCleanExit。
更好的长期修复
实现 AppShutdownCoordinator，把窗口、pipeline、pool、run registry、索引和 app-state 作为有序状态机关闭，并记录超时/未确认进程。
⏱ 预计工作量： 1–2 天  ·  回归测试：打包态启动长寿命假进程后 Cmd+Q，覆盖三种选择；退出后断言进程组消失或明确保持、cleanExit 与 registry 状态一致。

F-05. 坏 manifest 可阻断启动，重复 task ID 冲突会静默消失

HighConfirmed
🎯 Confidence: High📁 Data Integrity / Stability📍 src/main/storage/location-registry.ts:65-96; src/main/index.ts:199-211🧭 startup discovery

问题：发现器只忽略 ENOENT；任何单个非法 JSON/schema manifest 都抛出并使初始化失败。重复 task ID 虽被收集进 conflicts，启动代码却只消费 discovery.tasks。

为什么重要：一个坏任务可以让全部健康任务不可访问；重复副本则从队列静默消失，没有 identity-conflict 界面。

现实失败场景：同步盘产生截断的 task.json，Etch 整体无法启动；或用户复制任务目录做备份，两个副本都不再显示且无解释，容易诱发再次复制/删除。

最小修复
按任务隔离 parse 错误为 diagnostics/quarantine；把 conflicts 和 invalid manifests 纳入 bootstrap/queue 的显式恢复列表，禁止无提示丢弃。
更好的长期修复
实现 DiscoveryReport 持久模型：healthy/conflict/invalid/missing 四态、原始路径与可恢复动作；索引重建只处理 healthy，但 UI 始终显示其余状态。
⏱ 预计工作量： 1–2 天  ·  回归测试：同一 workspace 同时放健康、坏 JSON、旧 schema、重复 ID，断言 App 启动、健康任务可用且其他项出现在恢复摘要。

F-06. 外部进程 stdout/stderr 无界累积可导致 OOM

HighConfirmed
🎯 Confidence: High📁 Performance / Stability📍 src/main/runtime/process-runner.ts:253-265🧭 process I/O
